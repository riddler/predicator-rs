# The vendored conformance corpus

This directory holds the conformance material this crate is checked against.
Most of it is copied, byte for byte, from two other repositories at named
tags; five files are this repository's own. A copied file is never edited
here: not a case, not a schema, not a reformat and not a trailing-newline
fix.

## What is copied, and from where

From [riddler/predicator-ex](https://github.com/riddler/predicator-ex), the
reference implementation, at the tag `SOURCE.json` names:

- `manifest.json` - the corpus hash, the instruction-set version, and one
  entry per tier naming its file, the opcodes it unlocks and its case count.
- `corpus/tier-1.json` to `corpus/tier-10.json` - the cases, one JSON object
  per line (newline-delimited JSON, not a JSON array).
- `schema/case.json`, `schema/corpus.json`, `schema/manifest.json`,
  `schema/registry.json` and `schema/report.json` - the reference's schemas
  for an authored case, a case as the tier files carry it, the manifest, a
  registry and a runner's report.

The tag carries other conformance material beside these: the authored case
sources the tier files are generated from, a worked-example registry, and the
files and schemas of a third surface (the analysis surface) that sit outside
the corpus hash. This crate reads none of them, so none is copied.

From [riddler/predicator-ts](https://github.com/riddler/predicator-ts), the
TypeScript sibling, at the tag `transcript/VENDORED.json` names:

- `transcript/compile.json` and `transcript/compile-SOURCE.json` - what the
  reference answers over an authored list of sources no corpus case reaches
  (what it compiles, refuses and renders back to source, row by row, as each
  row's `kind` says), and the record of the run that wrote it.
- `transcript/tokens.json` and `transcript/tokens-SOURCE.json` - what the
  reference's lexer answers for a list of sources, and its record.

Each transcript was generated by running the reference itself, at the
reference tag its record names. That tag is older than the one `SOURCE.json`
names, so a row may give an answer the reference at the vendored tag no
longer gives. Such a row is not edited: it is listed in
`transcript/SUPERSEDED.json` (below). The records are copied as they are and
never re-stamped.

## What is this repository's own

- `SOURCE.json` - which copy of the corpus this is: the repository, the tag,
  the commit that tag resolves to, and the corpus hash and instruction-set
  version read out of the copied manifest. A tag identifies bytes and a
  branch does not, which is why a tag is what is recorded.
- `transcript/VENDORED.json` - which copy of the transcripts this is: the
  repository, the tag, the commit that tag resolves to, the directory they
  were copied from, and each copied file's SHA-256.
- `transcript/SUPERSEDED.json` - the transcript rows the reference at the
  tag `SOURCE.json` names answers differently. Its `tag` is that tag, and
  each element of its `rows` names the transcript (`file`), the row's 0-based
  line number in it (`index`), the row's own `source`, and the reference's
  `answer` at the tag, in the transcript's own spelling. A row is listed at
  most once. It starts empty.
- `registry.json` - the record of which cases this crate passes, on which
  surface, against which corpus. It is written only by `mise run ratchet`,
  from a run it makes, and never by hand.
- `README.md` - this file.

The code that reads all of it lives under `tests/conformance/`: the corpus
loader, the runner, the checks and the ratchet. None of it, and nothing in
this directory, is part of the published crate.

## The checks

`mise run gate:corpus`, a stage of the full gate, holds the copies to their
records:

- The SHA-256 of the tier files' bytes, concatenated in ascending tier
  order, equals the corpus hash in `manifest.json` and the one in
  `SOURCE.json`; each tier file holds its tier's `case_count` lines; no tier
  file sits in `corpus/` that the manifest does not list.
- Each transcript file's SHA-256 equals the one `transcript/VENDORED.json`
  records, every copied file in `transcript/` is listed there, and each
  transcript's own record carries the same hash in its `transcript_hash` and
  the transcript's line count in `counts.rows`.
- `transcript/SUPERSEDED.json` names the vendored tag, and each of its rows
  names a row that exists, by index and by its source. The stage prints how
  many rows it lists, per transcript.

A mismatch fails the gate naming the field that disagrees. It is never
repaired by rewriting a hash: the hash is what a claim of conformance is
anchored to, and a hash rewritten to match whatever is on disk anchors it to
nothing. The fix is to restore the copied bytes, or to vendor a new tag.

The runner reads every case of every tier on the evaluator surface, and every
case whose `source` is not null on the compiler surface, with no skip list; a
case carrying a key `schema/corpus.json` does not name is refused rather than
half-read, as is a case whose tier is not its file's and an id seen twice.
Each case is answered pass or fail. The evaluator surface runs the case's
instructions over its context; the compiler surface compiles its source with
`compile` and compares the instruction list, operand by operand, with the
case's. Tiers 6, 8 and 9 (statements, control flow and loops) hold no case
with a source, so the compiler's claim of tier 10 covers them with no entry.

`tests/compile_transcript.rs` answers four of the compile transcript's five
kinds of row: a compile row and a program row by the instruction list
`compile` or `compile_program` answers, a refusal row by its reason, message
and position, and a program refusal row by its message and position. The
counts are the transcript record's (`transcript/compile-SOURCE.json`): 63
compile, 35 program, 27 refusal and 29 program refusal rows. Its 45
decompile rows render a tree back to source text, which this crate has no
function for: they are out of scope until decompiling exists, and the test
counts them rather than answering them. A program row also records the
source span behind each instruction; the crate keeps no such table, so the
spans are not compared. Every row of those four kinds was checked against
the reference at the tag `SOURCE.json` names and none answers differently,
so `transcript/SUPERSEDED.json` lists none of them.

`mise run gate:registry`, also a stage of the full gate, holds
`registry.json` to the checks the reference's `RATCHET.md` gives a registry:
its pin is the manifest's corpus hash and instruction-set version, its
entries and claims are sorted and encoded one per line as that document
requires, every entry names a case of its surface at the case's tier, every
entry still passes in a run made now, and a claim of tier N has an entry for
every case it covers. A hand edit is refused because the file must be
byte-equal to what the writer produces from its own contents, and because an
entry no run passes fails the check. The stage prints, per surface, the cases
not yet claimed.

`mise run ratchet` is the one writer: it runs both surfaces and adds every
observed pass, refuses to drop an entry that no longer passes, and writes a
claim only when the entries support it. Claims are asserted through an
environment variable:

```bash
PREDICATOR_RATCHET_CLAIMS="compiler:10 evaluator:10" mise run ratchet
```

## The contract

The reference's `conformance/README.md` is the corpus contract (the two
surfaces, the tagged-value encoding, the cumulative tiers, retired cases and
the never-skip rule) and its `conformance/RATCHET.md` is the registry
contract. Read both at the tag `SOURCE.json` records, not at the reference's
default branch, because the copy here is that tag's. Where this file and
those documents disagree, they win.

## Refreshing to a new tag

A refresh is a deliberate, reviewed change, made by a person:

1. Copy each file listed above out of the new tag itself, byte for byte
   (`git show <tag>:conformance/<path> > <path>` in a clone of the source
   repository), never through an editor.
2. Re-record: write the new tag, its commit and the manifest's corpus hash
   and instruction-set version into `SOURCE.json`, or the new tag, commit and
   file hashes into `transcript/VENDORED.json`. A new corpus tag also
   re-reads every row of `transcript/SUPERSEDED.json` at that tag and moves
   its `tag`.
3. Run `mise run gate:corpus`, then the full gate, and read the diff like any
   other. A corpus whose hash moved also moves the registry's pin, so `mise
   run ratchet` is run in the same change; it re-pins the registry and
   refuses if an entry no longer passes.

Nothing in the build, the suite or the gate fetches from either repository
or updates these files as a side effect of anything else.
